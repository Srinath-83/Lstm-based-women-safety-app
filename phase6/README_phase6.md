# Phase 6 — The App (Frontend)

## What this is

A single-page web app that ties everything together: the safety heatmap
(Phase 4), live routing (Phase 4's grid-graph idea, running in the
browser this time), and an SOS button — all in one interactive interface
you can actually click through and demo.

**Everything runs client-side.** No backend server, no database. The
Python export script converts your existing CSVs into small JSON files;
the browser loads them once and does all the routing math itself with a
live implementation of Dijkstra's algorithm in JavaScript.

## Files


## How to run

```bash
cd phase6
pip install pandas numpy
python3 18_export_frontend_data.py
```

Then, because browsers block `fetch()` calls to local files opened
directly (`file://...`) for security reasons, you need to serve the
`app/` folder with a tiny local web server — this is standard practice,
not a workaround:

```bash
cd app
python3 -m http.server 8000
```

Then open **http://localhost:8000** in your browser.

## What you can do in the app

- **Click anywhere on the map** — sets your "current location" and pops
  up a live safety-score readout (the circular gauge)
- **"Route to Nearest Police" / "Route to Nearest Hospital"** — computes
  and draws two routes: a safety-weighted one (solid purple) and the
  true shortest one (dashed gray), plus a side-by-side stats comparison
- **The SOS button** — simulates the emergency flow: shows your
  coordinates, local safety score, and automatically routes you to the
  nearest police station, all annotated as "calculated offline, no
  network required"
- **Safety heatmap toggle** — turn the colored overlay on/off

## Design notes

The interface intentionally avoids a generic "AI dashboard" look — dark,
map-forward, high-contrast, styled more like an operations/dispatch
console than a typical web app. A few deliberate choices:
- The **risk-compass gauge** (the ring that appears when you tap the
  map) is the one signature interaction — it's meant to give an
  instant, at-a-glance safety reading, the core value proposition of
  the whole project, in a single glance
- Color scale is red→amber→teal rather than plain red→green, partly for
  accessibility and partly to avoid the most obvious "traffic light"
  cliché
- The pulsing SOS button and "OFFLINE-READY" badge are both deliberate,
  minor motion cues meant to communicate urgency/liveness — both respect
  `prefers-reduced-motion` for accessibility

## ⚠️ Things to know / test carefully on your machine

1. **Map tiles need internet.** The base map imagery (streets, labels)
   loads from a public tile server and needs an internet connection —
   this is normal and how virtually all web maps work; it's separate
   from the "offline routing" feature, which only needs your
   `frontend_data/` files, not tiles. Even with no internet, the
   heatmap, routing, and SOS logic will all still work — you'll just
   see a plain dark background instead of street imagery.

2. **I found and fixed a real bug while building this**, worth knowing
   for your report/viva: clicking on the map initially did nothing,
   because Leaflet's popups call `stopPropagation()` internally, which
   silently blocked my "set location on click" handler whenever the
   click landed on a heatmap cell with a popup bound to it. Fixed by
   removing the per-cell popups (the risk-compass readout already shows
   the same info) — a good example of a subtle event-bubbling bug in
   map libraries that's worth being able to explain if asked.

3. **This is a Python-simulated version of what a real Android app would
   do.** The actual routing math (Dijkstra, safety weighting) is
   identical to Phase 5's approach — here it's re-implemented in
   JavaScript so it can run live in a browser demo. For a real mobile
   app, this JS logic would be replaced by a proper offline routing SDK
   (GraphHopper/Valhalla, as discussed in Phase 5), but the underlying
   idea — prefer safer paths, work fully offline — is the same.
